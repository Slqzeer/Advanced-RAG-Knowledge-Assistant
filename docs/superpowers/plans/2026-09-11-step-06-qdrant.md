# Step 06 — Qdrant Indexing

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. Steps use `- [ ]` for tracking.

**Goal:** Store chunks and their vectors in the local Qdrant instance, idempotently, driven by one end-to-end script: `raw → clean → chunk → embed → upsert`.

**Architecture:** `app/retrieval/store.py` owns everything Qdrant. `app/core/config.py` appears here, because this is the first step with more than one environment variable to read. `scripts/index_corpus.py` wires the four existing stages together and is the first runnable artifact of the project.

**Tech stack:** `qdrant-client` (already installed), `pydantic-settings` (already installed). No new dependency.

## Decisions

**Point ids are `uuid5(NAMESPACE, chunk_id)`.** Qdrant accepts only integers or UUIDs, and `chunk_id` is a string. A deterministic UUID5 makes re-indexing an idempotent upsert instead of an accumulation of duplicates — which is what makes the script safe to run twenty times during step 12.

**Distance: cosine**, matching what the embedding model is trained for. Using dot product on un-normalised vectors, or euclidean on normalised ones, gives rankings that are wrong in ways that look plausible.

**Vector size is read from the model, not hardcoded.** Embed one probe string at startup and use its length. A collection created at the wrong dimension fails loudly at upsert, but only after you have paid to embed everything.

**A single unnamed dense vector.** Step 14 adds BM25 and may want a named sparse vector alongside, which means recreating the collection. That is fine: the step 05 cache makes re-indexing free and fast, so paying one re-index later is cheaper than carrying named-vector indirection through eight steps that do not need it. `ponytail:` comment this where the collection is created.

**Payload indexes on `source`, `document_id` and `language`, created now.** Two lines, and step 13's metadata filtering is then a query-time change instead of a re-index. Unindexed payload filters in Qdrant still work but scan, which silently turns into the thing you blame retrieval latency on.

**The full chunk text lives in the payload.** It costs disk and saves an entire second store plus the join between them. If payload size ever becomes a problem, that is a real measurement, not a guess.

**Config: one `Settings` class, read once.** `pydantic-settings` earns its place here — the alternative is `os.environ` scattered across five modules. `get_settings()` is `@lru_cache`-decorated: one line, and it is the whole singleton story.

## Tasks

### Task 1: Settings

- [ ] **Step 1: Failing tests** — defaults apply with a clean environment; an environment variable overrides a default; `get_settings()` returns the same object twice.

- [ ] **Step 2: Write `app/core/config.py`**

A `BaseSettings` subclass with `model_config = SettingsConfigDict(env_file=".env", extra="ignore")`. Fields: `qdrant_url`, `qdrant_collection = "chunks"`, `openai_api_key: str | None`, `embedding_model`, `embedding_cache_path`, `chunk_size = 1000`, `chunk_overlap = 200`, `top_k = 5`, `corpus_dir = Path("data/raw")`.

`extra="ignore"` matters: `.env` carries keys for later phases (`COHERE_API_KEY`), and a strict settings class would crash on them.

Do **not** make the API key required. Ingestion-free commands and the whole test suite must import this module without a key present.

- [ ] **Step 3: Green.** Commit: `feat(core): add application settings`.

### Task 2: The store

- [ ] **Step 1: Failing unit tests** — no server needed for these.

1. `point_id(chunk_id)` is deterministic across calls and differs for different chunk ids.
2. `point_id` returns a valid UUID string.
3. `chunk.to_payload()` round-trips through the payload→`Chunk` mapper without losing a field. Assert field-by-field against `Chunk.model_fields` so adding a field to the model without adding it to the mapper fails the test. This is the drift that makes search results lose their `url` three steps later.

- [ ] **Step 2: Write `app/retrieval/store.py`**

```python
def get_client(settings: Settings | None = None) -> QdrantClient: ...
def point_id(chunk_id: str) -> str: ...
def ensure_collection(client: QdrantClient, name: str, vector_size: int, *, recreate: bool = False) -> None: ...
def upsert_chunks(client: QdrantClient, name: str, chunks: Sequence[Chunk], vectors: Sequence[list[float]], *, batch_size: int = 256) -> int: ...
def collection_stats(client: QdrantClient, name: str) -> dict[str, Any]: ...
```

`ensure_collection`: return early if `client.collection_exists(name)` and not `recreate`; otherwise create with `vectors_config=VectorParams(size=vector_size, distance=Distance.COSINE)`, then `create_payload_index` for `source`, `document_id` and `language` as keyword fields.

`upsert_chunks`: assert `len(chunks) == len(vectors)` first — a mismatch here mislabels every vector in the batch. Build `PointStruct(id=point_id(chunk.chunk_id), vector=vector, payload=chunk.to_payload())` and upsert in batches of 256. Return the count.

Verify the exact client API against the installed version's docs rather than this plan; the universal `query_points` interface replaced the older `search` call, and similar renames happen.

- [ ] **Step 3: Write the integration test**

`tests/test_retrieval_store.py` with a `requires_qdrant` marker registered in `pyproject.toml`. A module fixture pings `/readyz` and calls `pytest.skip` when Qdrant is not up, so `uv run pytest` stays green on a machine without Docker.

Tests, against a throwaway collection named with a uuid suffix and deleted in teardown:

1. `ensure_collection` twice does not raise and does not wipe existing points.
2. Upserting 3 chunks reports 3 points in `collection_stats`.
3. **Upserting the same 3 chunks again still reports 3 points** — the idempotence guarantee.
4. `recreate=True` empties the collection.
5. A retrieved point's payload contains the chunk text and `source`.

- [ ] **Step 4: Green both with and without Qdrant running.** Verify the skip actually works by stopping the container. Commit: `feat(retrieval): index chunks in Qdrant`.

### Task 3: The indexing script

- [ ] **Step 1: Write `scripts/index_corpus.py`**

Arguments: `--source` (default all directories under `corpus_dir`), `--recreate`, `--limit N` (for a fast smoke run), `--dry-run` (everything except upsert).

Flow: load → clean → chunk → embed → ensure collection → upsert. Print a one-line-per-stage summary with counts and elapsed seconds, then a final total. Exit non-zero on failure.

`--dry-run` and `--limit` are not speculative features; they are how you avoid spending ten minutes and real money to discover a typo in the payload mapping.

- [ ] **Step 2: Smoke run**

```powershell
docker compose up -d qdrant --wait
uv run python scripts/index_corpus.py --limit 20 --dry-run
uv run python scripts/index_corpus.py --limit 20
```

- [ ] **Step 3: Full run**

```powershell
uv run python scripts/index_corpus.py --recreate
```

Record: document count, chunk count, point count, wall time per stage. Confirm the point count in the Qdrant dashboard at <http://localhost:6333/dashboard>.

- [ ] **Step 4: Re-run without `--recreate`** and confirm the point count is unchanged and the run is fast (everything cached). That is the idempotence proof on real data.

- [ ] **Step 5: Commit.** `feat(ingestion): add the corpus indexing script`.

## Definition of done

- The whole corpus is in Qdrant, with a known point count.
- Re-running the indexer changes nothing and costs nothing.
- Payload indexes exist on `source`, `document_id`, `language`.
- Payload round-trip is covered by a test that fails when the model and mapper drift.
- The test suite passes without Docker.

## Deliberately skipped

| Skipped | Add when |
|---|---|
| Named / sparse vectors | step 14 adds BM25 and the collection is recreated |
| Quantisation and HNSW tuning | the corpus is large enough for latency or memory to matter |
| Deleting points for removed documents | documents actually get removed |
| Qdrant auth and TLS | something other than localhost connects |
| Snapshots and backups | re-indexing stops being cheap |
| An async client | indexing or search throughput is the measured bottleneck |
