# Step 26 — Docker

## Goal

Make the service from step 25 reproducible with one command:

```console
docker compose up --build -d --wait
```

The Compose application contains the FastAPI service, Qdrant, and Redis. The
optional frontend from the original brief stays deferred because no frontend
exists yet.

## Contract

- Build one pinned Python 3.12 runtime image from `docker/Dockerfile` using the
  locked production dependencies in `uv.lock`.
- Run the API as an unprivileged user and bind it only to loopback by default.
- Keep Qdrant indexes, the fetched corpus, and API runtime data in named volumes. Redis remains an
  intentionally disposable cache, as established in step 23.
- Use Compose service DNS names inside the application network; local
  `localhost` defaults must not leak into the containers.
- Wait for Qdrant and Redis health checks before starting the API.
- Treat the image health check as liveness. `GET /health` remains the readiness
  check and can return `503` until the Qdrant collection has been indexed.
- Load `.env` when present without baking it or any secret into the image.

## Shape

- `docker/Dockerfile`: locked runtime image, corpus/index commands, and non-root process.
- `.dockerignore`: minimal, secret-free build context.
- `compose.yaml`: the complete three-service application and persistent data.
- `README.md`: container startup, first indexing, and verification commands.

## Execution

1. Verify the step-25 branch with Ruff, formatting, strict mypy, and pytest.
2. Add the runtime image and minimize its build context.
3. Add `rag-api` to Compose with healthy dependency ordering and container-only
   connection URLs.
4. Validate the resolved Compose model, build the image, and start the stack.
5. Verify container health and the API's readiness response without making a
   paid model call.
6. Re-run the complete local quality gates and publish the verified evidence in
   `README.md` and `docs/roadmap.md`.
